# KB증권 Open API 운영 조회 실습

## 과정 개요

- 대상: KB증권 계좌를 보유하거나 Open API 신청 절차를 학습하려는 학습자
- 목표: KB증권 Open API 신청·키 발급 절차와 공식 `dataHeader + dataBody` 요청 구조를 이해하고, 실제 운영 시세 조회를 안전하게 수행한다.
- 산출물: `.env` 형식 점검, 토큰·현재가·호가·차트 조회 기록

> KB B2C Open API는 공식 GitHub 기준 운영 환경을 사용한다. 이 과정은 읽기 전용 시세 API만 다루며 주문·잔고·정정·취소를 구현하거나 실행하지 않는다.

## 오전 — 계좌 선택과 Open API 신청 (3시간)

| 시간 | 학습자 활동 | 진행자/조교 역할 | 완료 기준 |
|---|---|---|---|
| 09:00–09:30 | KB증권 계좌·온라인 ID·Open API 포털의 관계를 이해한다. | 모의투자 화면과 운영 Open API의 차이를 설명한다. | 운영 API 호출의 의미를 이해한다. |
| 09:30–10:15 | KB증권 홈페이지의 `Open API 신청/조회`에서 신청 가능 계좌를 조회한다. | 비밀번호는 학습자만 입력하도록 안내한다. | 신청 계좌·이용 기간을 확인한다. |
| 10:25–11:10 | 해당 신청현황 행에서 App Key·App Secret을 확인한다. | 두 값이 반드시 같은 행에서 나온 한 쌍인지 확인한다. | 발급된 키 쌍을 안전하게 보관한다. |
| 11:10–12:00 | 서버의 `.env`를 설정하고 환경변수 전달을 이해한다. | Key 값을 보지 않고 변수 이름·설정 여부만 점검한다. | 앱이 환경변수를 읽을 준비가 된다. |

```ini
# 프로젝트 루트의 .env
KB_APP_KEY=발급받은_App_Key
KB_APP_SECRET=같은_행에서_발급받은_App_Secret
```

### 오전 핵심 개념

- KB 토큰 요청은 평면 JSON이 아니라 공통 요청 봉투를 사용한다.
- `grantType`은 camelCase이며 `dataBody` 안에 둔다.
- 일반 TR 조회도 `appKey`, `Authorization: bearer <token>`, `dataHeader`, `dataBody`를 사용한다.
- 공식 GitHub: <https://github.com/kbsecurities/kb-openapi>

```json
{
  "dataHeader": { "ipAddr": "서버_IP", "macAddr": "서버_MAC" },
  "dataBody": {
    "appKey": "...",
    "appSecret": "...",
    "grantType": "client_credentials"
  }
}
```

## 오후 — KB 연결·시세 테스트 + HTS 모의주문 화면 (3시간)

| 순서 | 웹앱 기능 | 역할 | 확인할 결과 |
|---|---|---|---|
| 1 | `/kb-api-test.html` 토큰 발급 | 인증 검증자 | Bearer 토큰 유형과 만료 시간만 확인한다. |
| 2 | 종목기본정보 | 데이터 구조 분석자 | 종목코드와 기본 필드를 확인한다. |
| 3 | 국내주식 현재가 | 시세 검증자 | `005930` 등 6자리 코드로 현재가 응답을 확인한다. |
| 4 | 호가·`/kb-chart.html` 통합차트 | 화면 기능 검증자 | KB IVS11560의 OHLCV만으로 캔들 차트가 그려지는지 확인한다. |
| 5 | 오류 기록 | 기록 담당 | HTTP 상태·업무 코드·발생 시각만 남긴다. |

### 이 웹앱의 KB 조회 API

```text
GET /api/broker-test/kb/token
GET /api/broker-test/kb/base-info?symbol=005930
GET /api/broker-test/kb/quote?symbol=005930
GET /api/broker-test/kb/orderbook?symbol=005930
GET /api/broker-test/kb/chart?symbol=005930&market=0&period=D&count=60
```

### 역할 분담

- 인증 담당: 토큰을 화면·로그·저장소에 남기지 않았는지 확인한다.
- API 담당: IVU10140(현재가), IVU10070(호가), IVS11560(통합차트)처럼 기능별 TR을 문서와 대조한다.
- UI 담당: 6자리 종목코드 검증과 오류 메시지 표시를 맡는다.
- 운영 담당: 운영 환경 호출량을 제한하고, 오류 발생 시 무한 재시도를 막는다.

### 연계 실습 — HTS 시뮬레이션·거래 이력 (60분)

KB의 운영 시세 조회와 이 웹앱의 주문 연습을 혼동하지 않도록, 주문은 독립된 학습용 HTS 흐름에서만 수행한다. KB API는 이 과정에서 계속 읽기 전용이다.

| 기능 | 구현·사용 순서 | 역할 | 확인 항목 |
|---|---|---|---|
| HTS 시뮬레이션 | `/hts.html`에서 종목 검색 → 관심종목 추가 | 화면 기능 담당 | 검색·현재가·관심종목 메모가 별도 API로 동작함을 확인한다. |
| 관심종목 메모 | 관심종목의 메모 저장 | 개인화 기능 담당 | 로그인 회원별로 저장되며, 종목코드와 메모 길이 검증이 필요함을 점검한다. |
| 주식 모의주문 | `/trade/stock.html`에서 1주 매수·매도 연습 | 주문 흐름 담당 | 이 주문은 웹앱 내부 모의체결이며 KB 운영 API 주문이 아님을 확인한다. |
| 내 거래이력 | `/trade/history.html`에서 출처 확인 | 대사 담당 | 주문 종류·수량·체결가·출처를 확인하고 실패 응답과 정상 체결을 구분한다. |

**구현 관점:** 운영 API 조회 실패를 모의 주문으로 대체하지 않는다. UI는 외부 조회 결과와 내부 모의체결 결과의 출처를 명확히 표시하고, 동일 버튼에서 두 종류의 주문을 섞지 않는다.

## 준비·설정 상세 (이 저장소 기준)

키 저장 위치와 기동 전 체크리스트는 `01.md`의 "준비·설정 상세"를 따른다. KB는 `.env`의 `KB_APP_KEY`/`KB_APP_SECRET`만 사용한다.

### 사전 가입·발급 절차 (오전 실습 상세)

| 순서 | 할 일 | 어디서 | 결과물 |
|---|---|---|---|
| 1 | KB M-able 앱 설치 → 비대면 계좌 개설(본인 명의 휴대폰·신분증) | 앱스토어, <https://www.kbsec.com> | KB증권 계좌 |
| 2 | 앱에서 KB증권 ID 등록, PC 웹 로그인용 클라우드 인증서 발급 | KB증권 홈페이지 | 온라인 ID, 인증서 |
| 3 | Open API → **Open API 신청/조회**에서 신청 가능 계좌 조회 → 계좌 비밀번호 입력 → API 그룹·이용기간·약관 동의 | KB증권 홈페이지 Open API 메뉴 (학습 페이지 링크 참고) | 신청 완료 |
| 4 | 신청현황의 **같은 행**에서 App Key·App Secret 확인 | 동일 메뉴 | Key·Secret 한 쌍 |
| 5 | `.env` 작성 (위 형식), 권한 600 | 저장소 루트 | 파일 준비 완료 |

- **리드타임 주의:** 인증서 발급·ID 등록·계좌 이용 등록은 심사에 따라 수 시간이 걸릴 수 있다. 실습 직전에 처음 신청하면 준비가 완료되지 않을 수 있으므로 계좌·ID 등록을 미리 마치도록 안내한다.
- KB는 모의투자 서버가 없고 **운영 API**다. 이 저장소는 조회 TR만 호출하며 주문 TR은 코드에 없다.
- 예비 키 쌍은 `.env`의 `KB_SECONDARY_APP_KEY`/`KB_SECONDARY_APP_SECRET`에 보존할 수 있지만 현재 앱은 사용하지 않는다.
- 앱이 사용하는 변수명은 `KB_APP_KEY`/`KB_APP_SECRET`으로 고정한다.

### 호출 대상과 TR

| 웹앱 API | KB 경로 (`https://developer.kbsec.com:32484`) | TR | dataBody 주요 필드 |
|---|---|---|---|
| `GET /api/broker-test/kb/token` | `/oauth2/token` | - | `appKey`, `appSecret`, `grantType=client_credentials` |
| `GET /api/broker-test/kb/base-info?symbol=` | `/api/v1/siqm4900` | SIQM4900 | `stnd_is_cd` |
| `GET /api/broker-test/kb/quote?symbol=` | `/api/v1/ivu10140` | IVU10140 | `excg_clsf=1`, `shrt_cd` |
| `GET /api/broker-test/kb/orderbook?symbol=` | `/api/v1/ivu10070` | IVU10070 | `is_cd`, `ovtm_mkt_clsf=0` |
| `GET /api/broker-test/kb/chart?symbol=&market=&period=&count=` | `/api/v1/ivs11560` | IVS11560 | `mkt_clsf=0/1`, `chrt_clsf=D/W/M/Y`, `inq_clsf=2`, `inq_cnt=10~300` |

- 모든 호출이 `{"dataHeader": {...}, "dataBody": {...}}` 봉투 구조다. 포털 요약 가이드의 평면 JSON 토큰 요청은 현재 발급 키에서 `E021`을 반환하므로 코드는 봉투 형식만 사용한다.
- 일반 TR 헤더는 `Authorization: bearer <token>`(소문자 bearer)과 `appKey`다. `dataHeader`에는 서버의 IP·MAC을 채운다(공식 테스트 앱 동작 모사).
- 매 조회마다 토큰을 새로 발급한다(KB는 캐시 없음). 연속 클릭은 운영 서버에 토큰 요청을 반복시키므로 막는다.
- 토큰은 되는데 조회가 거부되면 신청 시 선택한 **API 그룹**에 해당 TR이 포함됐는지 확인한다.
- 통합차트의 정상 업무코드는 `0024`이며, `out2`의 `dt`, `opn_prc_p2`, `hgh_prc_p2`, `lw_prc_p2`, `cls_prc_p2`, `vlm`을 캔들로 정규화한다. KOSPI는 `mkt_clsf=0`, KOSDAQ은 `1`을 사용한다.
