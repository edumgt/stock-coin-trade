# 빗썸 공지 레이더 평가 (외부 판정 모델)

빗썸 공지 제목 한 건을 `src/deskjev/notices.py`가 "실행 위험"(입출금 중단·예정, 거래유의 지정·거래지원 종료, 외부 거래소 대상 출금 주의)으로 맞게 가려내는지 잰다. 위험 확률 임계값(`notices.RISK_MIN`)은 이 평가로 정한다.

## 사례 (`cases.jsonl`, 155개)

| 필드 | 뜻 |
|---|---|
| `id` | `r01`~`r20` 실제, `s001`~`s135` 합성 |
| `source` | `real`: 2026-09-26 08:51 KST에 `GET https://api.bithumb.com/v1/notices?count=20`으로 받은 20건 전부(제목·분류·게시 시각·URL 원문 그대로). `synthetic`: 관찰한 제목 양식을 따라 만든 135건(URL 없음) |
| `title`, `categories`, `published_at`, `url` | API 응답 필드. `published_at`은 KST `yyyy-MM-dd HH:mm:ss` |
| `risk` | 김프 화면에 "확인 필요"로 띄워야 하는가 |
| `kind` | `suspend`(입출금 중단·예정) · `caution`(거래유의 지정·기간 연장·투자유의 촉구·거래지원 종료) · `external`(외부 거래소 대상 출금 주의·제한) · `none` |
| `coins` | 티커 목록(제목 괄호 속 표기 그대로, 네트워크 계열은 네트워크 티커) · `"ALL"`(거래소 전체 자산, 외부 거래소 주의) · `"UNKNOWN"`(대상 불명) |

**라벨은 에이전트(Claude)가 달았다. 노아 검수 전이다.**

라벨 기준
- 기준 시각은 **2026-09-26 09:00 KST**(`eval_notices.REF_NOW`). "(09/25 재개)"처럼 재개일이 이 시각 이전(당일 포함)이면 끝난 중단이라 `none`, 이후면 `suspend`.
- 날짜 없는 중단 공지(예: "코스모스(ATOM) 입출금 일시 중지 안내")는 본문 없이 끝났는지 알 수 없으므로 `suspend`로 둔다("확인 필요").
- 하드포크·네트워크 업그레이드 "지원", 지갑 점검, 입출금 지연처럼 "중지" 낱말이 없어도 전송이 멈추거나 늦어지는 공지는 `suspend`.
- 원화 입출금·수수료·최소 출금 수량·데스티네이션 태그 안내는 가상자산 전송 위험이 아니라 `none`.
- 합성 공지의 분류는 관찰한 값(`입출금`·`거래유의`·`점검`·`안내`·`이벤트`·`신규서비스`)만 썼다. 거래지원 종료 공지의 실제 분류 이름은 확인하지 못했다(미검증).

섞은 유형: 재개 완료(오경보 유발), 재개일이 미래인 중단, 시작 시각이 미래인 예정 중단, 코인명이 든 이벤트·에어드랍·스테이킹·신규 상장, 네트워크 계열 N종, 거래소 전체 중단·전체 서비스 점검, 외부 거래소 대상 주의, 거래유의 지정·해제, 거래지원 종료·철회, 김프 화면 8개 코인(BTC ETH XRP SOL DOGE ADA TRX LINK)의 공지. 위험 76건, 위험 아님 79건.

## 실행

```bash
# 규칙만(무료)
PYTHONPATH=src:python-stock-backend python -m deskjev.eval_notices --mode rules
# 정답을 확률 0.99로 돌려주는 가짜 판정 모델(무료). jev 정책이 100%가 아니면 채점기나 라벨이 틀렸다.
PYTHONPATH=src:python-stock-backend python -m deskjev.eval_notices --mode oracle
# 실제 판정 모델(과금). 비용 상한 없이는 실행하지 않는다. 155건 한 번에 실행한다.
PYTHONPATH=src:python-stock-backend TYPESAFE_API_KEY=... python -m deskjev.eval_notices --mode live --max-usd 1
```

이 Mac에서는 `.venv` 파이썬이 네이티브 확장 import에서 멈춰 `sct-test:dev` 컨테이너로 돌렸다(`docker run --rm -e TYPESAFE_API_KEY -v "$PWD":/repo -w /repo -e PYTHONPATH=src:python-stock-backend sct-test:dev python -m deskjev.eval_notices ...`).

실행하면 `results/<mode>.json`(요약 + 사례별 행)에 쓴다. 저장소에는 live 결과만 둔다. oracle은 구성상 100%이고, 규칙만 정책의 지표는 `live.json`의 `policies.rules`에 있다. `results/live-risk_min-0.3.json`은 임계값을 정하기 전 첫 live 실행(RISK_MIN 0.3)이고, `results/live.json`은 0.4로 정한 뒤 다시 돌린 결과다.

## 정책과 채점

oracle·live는 사례마다 판정 모델을 **한 번만** 부르고 그 답을 두 정책이 함께 쓴다.

- **rules**: 규칙 → 못 정하면 폴백(분류가 `입출금`·`거래유의`·`점검`이면 종류 불명 경고, 아니면 위험 아님)
- **jev**: 모든 공지를 판정 모델이 판정(티커 추출만 코드)
- **rules+jev**: 규칙 → 규칙이 못 정한 공지만 판정 모델. 서비스가 쓰는 정책

지표: 위험 재현율(목표 ≥95%), 정밀도, 오경보율(위험 아님 중 경고 비율), 맞게 잡은 위험의 종류·대상 코인 정확도, 판정 모델이 판정한 공지의 위험 확률 보정(ECE, 구간 6개), 지연(규칙 판정은 0 ms).

실제 공지 20건만 보면 세 정책 모두 재현율 100%이고, 오경보율은 rules 0%, jev 60%(재개일이 지난 "(MM/DD 재개)" 공지 9건), rules+jev 0%다. rules+jev는 실제 20건 중 2건만 판정 모델에 물었다.

- **규칙만으로도 실제 공지 20건에서는 틀린 판정이 없었다.** 합성 공지에서 규칙(폴백)이 놓친 4건(하드포크·토큰 스왑·리디노미네이션 "지원", 상장폐지 예정)과 폴백 오경보 11건이 차이를 만든다. 그래서 판정 모델은 규칙이 못 정한 공지에만 쓴다.
- **판정 모델만 쓰면 안 된다.** 날짜 비교를 맡기지 않았으므로 "(09/25 재개)"를 진행 중 중단으로 본다.
- rules+jev가 놓친 1건: `s051` "폴카닷(DOT) 리디노미네이션 지원 안내"(위험 확률 0.27·0.31). 오경보 4건: 원화 입출금 중단(`s065`), 데스티네이션 태그 안내(`s068`), 사칭 피싱 주의(`s125`), 투자 위험 고지(`s129`).
- 규칙이 판정한 공지(102건)는 oracle 실행에서 rules+jev가 100%이므로 모두 라벨과 같다.

## 한계

- 같은 입력으로 live를 두 번 돌리면 위험 확률이 최대 ±0.09 달라졌고, 경계 근처의 종류·범위 답이 몇 건 바뀌었다(두 결과 파일 비교, 확률 차 0.02 초과 또는 답이 바뀐 사례 28건). 입력 토큰 수는 두 번 모두 136,994로 같았다.
- 합성 135건은 에이전트가 쓴 제목이다. 실제 공지의 분포(대부분 "입출금 일시 중지 안내 (MM/DD 재개)")와 다르다.
- 제목만 본다. 본문(중단 시각·대상 네트워크 목록)은 수집하지 않는다.
- 지연은 이 Mac(한국)의 Docker에서 잰 값이다.
- 하루 호출량은 실제 20건의 게시 간격(하루 약 6.4건)과 실제 공지의 판정 모델 비율(10%)로 어림했다. 같은 제목은 프로세스 캐시로 다시 과금하지 않으므로 상한에 가깝다.
